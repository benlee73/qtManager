# 신청자 관리 정보구조 정비 설계

## 목적

신청자 관리 화면에서 검색 결과가 적을 때 목록 행이 비정상적으로 늘어나는 문제를
해결하고, 신청자 한 명의 현재 구독과 과거 이력, 신청자 메모 및 연결된 확인할 일을
한눈에 구분할 수 있게 한다. 현장 배부 화면과 동일한 글자 체계, 테마 색상 및 정보
밀도를 유지한다.

## 범위

- 신청자 목록 행 높이와 정보 배치
- 상단 관리 기능의 시각적 우선순위
- 오늘 날짜가 속한 호를 기준으로 한 구독 이력 구분
- 신청자 상세의 신청자 메모와 연결된 확인할 일
- 배부 이력의 열 구조와 테마별 경계선
- 관련 도메인·애플리케이션·인프라 조회, UI, 문서, 로그·업무 변경 이력 및 테스트

신청자 등록·수정·갱신·보관, 검색 조건, 배부 자격과 SQLite 저장 형식은 변경하지
않는다.

## 기준 호와 업무 규칙

- 신청자 관리의 구독 이력 강조 기준은 오늘 날짜가 실제로 포함된 QT 호다.
- 1~2월은 1~2월호, 3~4월은 3~4월호처럼 두 달 단위로 계산한다. 예를 들어
  2026년 8월 3일의 기준 호는 `2026년 7~8월호`다.
- 이 기준은 신청자 관리 화면의 시각적 분류에만 사용한다.
- 실제 배부 자격, 대상·완료·남음·배부 통계와 배부 가능 수량은 현장 배부 화면에서
  사용자가 선택한 호를 기준으로 계산한다.
- 구독은 기준 호와 구독 기간을 비교해 다음 상태로 표시한다.
  - `현재`: 기준 호를 포함하는 보관되지 않은 구독
  - `예정`: 시작 호가 기준 호보다 뒤인 보관되지 않은 구독
  - `지난 구독`: 마지막 호가 기준 호보다 앞인 보관되지 않은 구독
  - `보관됨`: 보관된 구독. 기간 상태보다 보관 상태를 우선 표시
- 현재 구독을 먼저, 예정 구독을 그다음, 지난 구독과 보관 구독을 뒤에 배치한다.
  같은 상태 안에서는 최근 시작 호가 먼저 보이게 한다.

## 아키텍처와 데이터 흐름

권장한 도메인 기반 상세 조회 확장 방식을 사용한다.

1. 데스크톱 어댑터가 로컬 시스템 날짜를 읽어 오늘이 포함된 기준 호를 만든다.
2. 신청자 상세 조회 유스케이스는 기준 호를 명시적으로 받아 각 구독에 기간 상태를
   부여한다. 기간 비교에는 기존 `Issue`와 `Subscription` 도메인 규칙을 재사용한다.
3. 신청자 관리 저장소 포트는 선택한 신청자에게 연결되고 보관되지 않은 확인할 일만
   조회한다.
4. SQLite 어댑터는 `check_items.person_id`를 사용해 해당 항목을 최신 수정 순서로
   조회한다.
5. 상세 응답은 구독 상태와 연결된 확인할 일을 함께 반환한다. UI는 문자열을 다시
   해석하거나 전체 현장 배부 데이터를 가져오지 않는다.

기존 테이블과 연결 컬럼을 그대로 사용하므로 SQLite 마이그레이션은 추가하지 않는다.

## 화면 설계

### 신청자 목록

- 목록 컨테이너의 행을 내용 높이로 고정한다. 결과가 적으면 남은 공간은 목록 아래의
  빈 공간으로 남으며 각 신청자 카드가 늘어나지 않는다.
- 각 행은 또래 배지와 다음 세 줄을 사용한다.

```text
[94] 원예진
     정식 등록 · 구독 2건
     2026년 11~12월호까지
```

- 전화번호는 목록 행에서 제거한다.
- 이름·또래·전화번호 검색 기능과 오른쪽 상세 화면의 전체 전화번호는 유지한다.
- 선택 상태는 현장 배부 화면과 같은 얇은 강조선과 낮은 채도의 배경으로 표시한다.

### 상단 기능

- `데이터 백업·복원`, `Google 응답 붙여넣기`, `신청자 등록`을 모두 항상 표시한다.
- 자주 사용할 수 있는 `데이터 백업·복원`을 더보기 메뉴로 숨기지 않는다.
- `신청자 등록`만 주 색상 버튼으로 표시하고 나머지 두 기능은 크기가 작은 보조
  버튼으로 표시한다.
- 현재 기능과 테스트 식별자는 유지하고 화면 문구만 간결하게 정리한다.

### 신청자 상세

- 이름, 또래, 전체 전화번호와 수정·갱신 기능을 상단에 유지한다.
- 신청자 메모 영역은 내용 유무와 관계없이 항상 표시한다. 내용이 없으면
  `등록된 신청자 메모가 없습니다.`를 보여주며 정보 수정으로 입력할 수 있음을 알린다.
- 연결된 확인할 일 영역은 신청자 메모 바로 아래에 둔다.
- 보관되지 않은 `확인 필요`와 `확인 완료`를 모두 표시하고 기존 체크박스 표현으로
  상태를 구분한다. 이 화면에서는 읽기만 제공하며 상태 변경과 보관은 현장 배부
  화면에서 수행한다.
- 확인할 일이 없으면 `연결된 확인할 일이 없습니다.`를 표시한다.

### 구독 이력

- 현재 구독은 가장 높은 시각적 강조와 `현재` 상태를 사용한다.
- 예정 구독은 중립적인 보조 강조와 `예정` 상태를 사용한다.
- 지난 구독은 낮은 대비의 배경과 `지난 구독` 상태를 사용한다.
- 보관 구독은 가장 낮은 대비와 `보관됨` 상태를 사용한다.
- 색상만으로 상태를 구분하지 않고 상태 문구를 함께 제공한다.
- 기간, 매 호 수량, 신청 출처와 신청일, 구독 메모는 기존처럼 보존한다.

### 배부 이력

- 목록 위에 `배부 호`, `처리`, `처리 시각` 열 제목을 표시한다.
- 처리 수량과 시각은 고정폭 숫자와 일관된 정렬을 사용한다.
- 행 구분선은 하드코딩한 밝은 색을 제거하고 라이트·다크 테마 공통 경계 토큰을
  사용한다.
- 배부 취소 이력은 기존처럼 `취소 N권`으로 명시한다.

## 오류와 빈 상태

- 기준 날짜 또는 호 계산에 실패하면 신청자 상세 조회를 임의 상태로 표시하지 않고
  기존 오류 알림 경로로 전달한다.
- 연결된 확인할 일 조회가 실패하면 다른 상세 데이터만 부분 표시하지 않고 상세 조회
  전체를 실패 처리해 서로 다른 시점의 정보가 섞이지 않게 한다.
- 구독, 배부, 신청자 메모와 확인할 일이 없는 경우 각각 독립적인 빈 상태를 표시한다.

## 테스트와 검증

- 도메인·애플리케이션 단위 테스트
  - 1~2월부터 11~12월까지 오늘이 포함된 호 계산
  - 연도 경계와 2026년 8월 3일 → 2026년 7~8월호
  - 현재·예정·지난 구독 및 보관 우선 상태
  - 상태별 정렬과 여러 권·서로 다른 기간 구독 보존
- SQLite 통합 테스트
  - 선택한 신청자의 보관되지 않은 확인할 일만 반환
  - 확인 필요·확인 완료 보존, 다른 신청자와 보관 항목 제외
  - 신청자 메모와 구독·배부 이력 무손실 조회
- UI 단위 테스트
  - 목록에서 전화번호를 숨기되 검색 안내는 유지
  - 신청자 메모와 연결된 확인할 일의 내용 및 빈 상태
  - 구독 상태별 클래스·문구와 배부 이력 열 제목
- Tauri E2E
  - 검색 결과가 적을 때 신청자 행이 내용 높이를 유지
  - 현재·지난 구독 시각 구분
  - 신청자와 연결된 확인할 일 및 신청자 메모 표시
  - 라이트·다크 모드의 배부 이력 경계선과 내부 스크롤
  - 상단 세 기능의 노출과 주·보조 버튼 위계
- 최종 검증은 `just check`, macOS 로컬 Tauri E2E와 실제 앱의 라이트·다크 화면
  캡처 비교로 수행한다. GitHub Actions 무료 사용량 차단 기간에는 Windows 자동
  검증을 실행하지 않고 미완료 사항으로 명시한다.

## 문서와 변경 기록

- `PROJECT_SPEC.md`의 요구사항, 화면 구조, 업무 규칙, ADR, 로드맵과 변경 이력을
  갱신한다.
- 사용자 안내서와 도움말에서 신청자 관리 상세 정보의 의미를 설명한다.
- 개인정보가 포함된 값은 애플리케이션 로그나 업무 변경 이력 요약에 기록하지 않는다.
- 조회 자체에는 새 운영 로그를 만들지 않는다. 상세 조회 실패와 기존 고정 이벤트
  로그 정책은 유지한다.
